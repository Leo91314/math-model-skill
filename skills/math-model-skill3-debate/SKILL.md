# 人机讨论：从理解到可检验主张

用户提出自己的理解，我们共同质疑、修正和形成研究方案。讨论追求对题目更合适的决定，不追求辩论输赢、附和或固定轮数。首次使用读 [共同约定](../math-model-skill1-read/references/principles.md)，复用题面、用户原话、第2步来源和已知结果。

## 先准确承接用户的想法

用简短文字重述用户的研究对象、核心直觉和打算解决的困难，保留其合理部分；把表达不完整与数学不成立区分。若尚未给出个人想法，先基于现有材料给出可讨论的候选与最关键分歧，询问用户的理解，不把自己的方案写成双方共识。

将发散想法拆成可判断的陈述：题目事实、用户猜想、必要假设、模型关系、算法设想和预期结论。能从原文解决的疑问先自己核对；不要求用户逐项批准符号、实现细节和已授权选择。

## 每轮只处理有价值的分歧

1. **给想法最合理的数学表达。** 定义对象、已知/待估/可控量、目标、约束、状态关系、初边值及跨问接口。检查是否真正回答题目，是否在不知不觉间缩小方案集、换平均口径或丢失全过程约束。
2. **明确支持理由与最强反对理由。** 依据原题、推导、数据和已读文献指出成立条件、潜在反例与替代解释。优先讨论会改变结论的分歧，而非个人算法偏好；用户方案成立时直接认可，不为“博弈”制造异议。己方观点被反证时也应修正。
3. **设计能区分观点的检查。** 用关键推导、边界例、小实例或必要数据对照回答当前分歧，说明不同结果如何改变决定。纯讨论范围先给检查设计；用户已授权小检验时可实际执行，未运行不得写成证据。缺一般证明时可继续探索，并区分等价、筛选、近似、受限策略与启发式。
4. **比较模型与方法的组合。** 围绕本题的正确性、解释力、实施成本、所需数据、可验证性及后问复用取舍。模型描述规律和决策，算法负责求解；换更复杂的优化器不自动产生贡献。合理的结构转化可以直接作为首个可信解，不强制先实现传统方案。
5. **收敛到当前证据支持的方案。** 给出采用、保留待验、收窄或放弃的判断及理由，说明尚未消除的分歧。所谓“最适合”应限定在现有输入、目标、预算和比较范围，未知效果不承诺为最佳。关键科学选择仍需用户表态时提出一个最影响路线的问题，保留讨论状态；其他独立分析可继续。

## 把贡献和问题绑定

当方案已足够清楚，整理一张简短的“主张与证据”卡，避免提前写满论文：

- **问题与瓶颈：** 原题哪项任务需要解决，现有或直观路线为什么存在具体困难。
- **核心观察与方法：** 哪个结构、机制或数据事实支持何种模型/转化，关键假设在哪里使用。
- **拟主张与贡献：** 这一方法预计或已经改变什么，如减少维数、提高可靠性、解释机制或改善决策；明确属于题设应用、适配、推导还是经核实的新发现，不默认具有文献首创性。
- **对应证据：** 每项主张需要哪条证明、什么对照、何种约束核验或什么数据，什么结果会推翻它。
- **边界与接口：** 适用条件、尚待检验之处，以及第4步需要的输入、方程、算法候选和输出。

有真实结果才写定量提升；“预期”与“已支持”分别标明。证明某表示等价的价值与其是否实测更快分开；没有性能提升不必抹去成立的结构贡献。

## 本轮交付与衔接

短讨论在聊天中给“我理解的思路、最关键的判断、当前方案和待决点”；重要决策可记入 `outputs/workflow/03-debate.md` 或已有记录，不抄完整对话。交付可继续研究的模型说明与主张卡，不设置固定回合、对立角色数量、评分或全部假设签字流程。

用户已明确认可路线或授权自主选择时，按授权衔接第4步或必要的小检验，不再问一次批准。尚未给出决定时，不将沉默当同意，不替用户编造核心观点，也不推进依赖该选择的完整实验。正式参赛的核心建模与分析按当届要求由队伍主导，AI产出需要真实的人工核验。
