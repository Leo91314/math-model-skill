# 数模提示词：按当前阶段挑一条使用

以下模板适用于当前工作区，方括号内容按实际情况替换。不要一次粘贴全部模板。题面、原始附件和当前版本比长篇角色设定更重要。指令中的“运行成功”必须有真实执行证据；AI 使用与提交方式以当届比赛要求为准。

## 1. 题目刚发布：启动读题和基线

```text
题面和全部附件已提供。使用 $bzd-problem-translator 和 $bzd-modeling-ideas，先完整理解题目，再开始求解。
提取每问的输入、输出、单位、约束、评价标准及问间依赖，区分题目明确给出的条件与我们增加的假设。把重要判断对应到题面位置或数据字段。
最多保留三条有依据的候选路线，比较数据是否支持、实现成本、可解释性及失败条件，并推荐一条。
对可独立的题意核对、数据检查、算法资料查证使用子代理并行推进；主任务负责跑通最小基线。用项目 .venv/bin/python 实际运行，返回初步结果、主要误差或约束残差、代码与复现命令。
只有阻塞求解的缺失信息才提问；其他不确定性显式记录并继续可做的工作。第一轮以可运行基线为交付，不急于写完整论文。
```

## 2. 数据检查：先弄清附件能支持什么

```text
检查 data/raw/ 中的全部附件，建立字段含义、单位、观测对象、采样时间与文件关系表。核查缺失、重复、异常值、编码、时空对齐，以及可能的数据泄漏。
不要默认删除异常值或插值补齐。对每项处理说明理由和对各问的影响，保留原件，把必要的处理写成可重复运行的脚本。
输出：影响解题的主要数据问题、可支持和不能支持的模型判断，以及最小清洗脚本。没有的数据明确写缺失，不用演示数据替代。
```

## 3. 模型选型：判断复杂模型是否值得做

```text
针对第[几]问，比较当前基线与[候选模型]。必要时使用 $bzd-model-dictionary，但以题意、数据及原始文献为判断依据。
重点判断模型是否回答了目标问题，参数是否可辨识，假设是否可信，约束是否完整，以及新增复杂度能否产生可验证的收益。
用同一组输入、评价指标、数据划分和合理计算预算比较；数据划分要尊重时间顺序或组间依赖。先完成基线，再决定是否升级，不为增加算法名而叠加模型。
最终明确推荐方案、决定性依据、适用边界和下一项最有价值的验证。
```

## 4. 卡住或报错：定位根因再修改

```text
当前问题是：[症状、错误信息、运行命令、预期行为]。
先最小化复现，再区分根因属于数据、数学模型、数值算法、代码实现还是运行环境。给出支持主要假设的直接证据，然后做范围最小的修复。
用同一个失败案例验证修复，并检查它是否改变核心结果。若失败证据否定当前路线，重新选择路线，不连续添加补丁或无依据调参。
```

## 5. 独立复核：主动找会推翻结果的问题

```text
作为独立复核者，对照原题、当前代码、参数和实际输出检查我们的主要结论。有相关论文段落时使用 $bzd-model-solution-checker。
优先查单位、数量级、初始/边界条件、约束遗漏、目标函数方向、参数可辨识性、优化可行性，以及数值误差。预测任务还需检查数据泄漏和验证设计。
尝试用解析特例、极端输入、独立求解器或必要的小实验复核；区分模型合理性、实现正确性和结果有效性。
只列影响最大的三个风险，附可复现证据和最小修正建议。不要为了凑数量制造问题，也不要将尚未验证说成确定错误。
```

## 6. 鲁棒性：检验结论能否站住

```text
检查当前主结论对关键参数、测量误差和假设是否敏感。先确定最可能改变决策的因素，为扰动范围给出数据或文献依据，再选择适当的局部或全局分析。
把数值离散误差、参数不确定性、随机仿真误差和模型结构偏差分开讨论。报告结论保持成立的范围、可能失效的条件，以及这对题目要求的实际含义。
无需机械地对所有参数都做相同比例的扰动，也不要用没有依据的置信区间制造确定性。
```

## 7. 论文图：先说明图要证明什么

```text
使用 $nature-figure，后端明确选 Python。基于[已验证的结果文件]制作论文图，图要支持的结论是：[一句话结论]。
先判断现有结果是否支持这句话，再选择必要的图形；如果支持不足，明确指出缺什么证据。
统一单位、字体、配色、坐标与图例，明确误差线或阴影带的含义。使用适合中文数模论文阅读的字号和版面，不机械套用期刊尺寸。导出 PDF、SVG 和预览 PNG，并保留绘图脚本及作图数据。
检查页面中的文字、遮挡和裁切；不要为了视觉效果改动数据、隐藏反例或夸大坐标差异。
```

## 8. 论文整合：让结果形成一条主线

```text
根据当前已验证的模型、代码输出和图表，整合[指定章节或全文]。先用一句话明确全文核心发现，再组织“问题—模型依据—求解—结果—解释—适用边界”的叙述。
让各问共享必要的符号和模型，删除重复推导、无结果支撑的创新宣称及流水账。每个关键数值和结论都应能追溯到对应计算结果。
修改意见应自然融入主线，不要把正文写成逐项答复审稿人。不新增未经计算的结果，不编造文献。
输出格式为[Markdown/Word/LaTeX]；需要正式排版时遵循已提供的当届规范。材料不足的地方明确标注待补，不伪装成完整结论。
```

## 9. 引文核对：检查文献是否真的支持论断

```text
核查[章节或参考文献列表]：逐条验证文献是否存在，作者、年份、标题和 DOI 是否一致，以及它是否真正支持文中的具体论断。
优先读取原论文、官方文档或公开原始数据来源。只能看到摘要或检索片段时，标注核验范围；无法核实的条目标记待核实，不编造替代引用。
最终给出需要保留、修改或删除的条目与证据，按已提供的比赛格式整理引用。实质使用的 AI 工具也应按真实记录和当届规则披露。
```

## 10. 时间紧张：收敛并交付

```text
距离提交还剩[时间]。请读取现有题面、任务记录、代码、结果和论文，按“遗漏题目要求/影响正确性/影响表达”评估剩余工作。
优先完成足以改变结论或影响交付的事项，给出少量明确任务并立即执行已授权部分。除非发现致命问题，不临时更换已经验证的主模型。
最终核对各问答案、摘要数值、图表引用、符号单位、附件和官方提交要求的一致性，交付可打开的最终文件、复现入口和尚未解决的真实限制。
```

## 两条随时可用的短指令

**防止工作越做越大：**

```text
请收敛到当前问题的最小可行解。先复用已有数据、代码和依赖，跑通关键路径；复杂度增加必须能解释它改善了什么。保留必要的正确性验证，不扩大到无关重构和流程建设。
```

**换会话后继续：**

```text
先读 AGENTS.md、README.md、task_plan.md、findings.md、progress.md，并检查当前文件与记录是否一致。简短说明已验证的结果、仍未解决的问题和下一步，然后继续执行。除非发现变更或疑点，不从头重复已通过的工作。
```
